# 03 · 领域模型与算法

> 本文是系统的「确定性内核」：什么算冲突、一门课算进哪个模块、指标怎么算。
> 代码：`packages/shared/src/{types,week,conflict,progress,metrics}.ts`，前后端共用。
> 原则：**任何结论都必须可解释**——界面上不出现无法回答「为什么」的数字。

---

## 1. 模型总览

```
Term (学期)
  └─ Section (教学班) ── n:m ── Course (课程)
        │                        │
        │ 1:n                    │
        ▼                        ▼
     Meeting (排课)          RequirementNode (培养要求节点)
     · day 1-7               · requiredCredits
     · start/endPeriod       · rule: courseSet | tagSet | elective
     · WeekPattern           · children[]

StudentProfile ── TranscriptRecord[] ── Plan[]
                                        └─ PlanItem { sectionId, status }
                                              ├─ selected → 上课表、计学分
                                              └─ backup   → 仅暂存
```

### 1.1 关键不变量

| 不变量 | 说明 |
| --- | --- |
| 一个 `Plan` 只属于一个学期 | 跨学期规划尚未支持；`Plan.termId` 决定可选教学班集合 |
| `PlanItem.sectionId` 必须属于该学期 | 服务端 `PUT /items` 校验，跨学期教学班直接 400 |
| 一个教学班在同一方案中只出现一次 | 服务端按 `sectionId` 去重 |
| `Course.code` 是课程号，`Section.id` 是教学班实例 | 同一门课可有多个教学班，学分只算一次 |
| 一门课只计入一个培养模块 | 见 §4 分配算法 |
| 成绩记录 `creditsEarned` 与 `status` 一致 | `passed` 才 > 0；`in-progress` 恒为 0 |

## 2. 教学周：位掩码

### 2.1 为什么

冲突判定本质是集合求交：两门课只要在「同一星期、同一节次、同一周」重叠，就冲突。
把周次压成 32 位整数后，求交就是 `maskA & maskB`，单双周、跳周、分段周一次处理完。

```
bit 0 → 第 1 周
bit 1 → 第 2 周
...
bit 30 → 第 31 周（上限）
```

### 2.2 `WeekPattern` 的三种形态

| 形态 | 示例 | 展开结果 | 展示文案 |
| --- | --- | --- | --- |
| 连续 | `{from:1,to:16,parity:'all'}` | 1..16 | `1-16周` |
| 单/双周 | `{from:1,to:16,parity:'odd'}` | 1,3,…,15 | `1-16周（单周）` |
| 跳周 | `{from:1,to:16,parity:'all',explicit:[1,2,10]}` | 1,2,10 | `1-2,10周` |

> 注意 `formatWeekPattern` 对单双周按**名义区间**展示（`1-16周（单周）`），而不是 `1-15周`。
> 后者会让用户误以为课程只上到第 15 周。

### 2.3 解析原始文本

`parseWeeksText()` 支持教务系统常见的写法：

```
"1-16周"            → 1..16
"第1-16周(单)"       → 1,3,..,15（parity=odd）
"3-11周(单),13-16周" → 3,5,7,9,11,13,14,15,16（explicit）
"1,3,5,7周"         → 显式列表
```

解析失败返回 `null`，调用方保留原文并标记待确认——**宁可显示「周次待确认」，也不丢课**。

## 3. 冲突检测

### 3.1 规则表

| 类型 | 严重度 | 触发条件 | 文案模板 |
| --- | --- | --- | --- |
| `time` | error | 同日 + 节次区间相交 + 周次集合相交 | 《A》与《B》在周三 第 3-4 节 冲突，重叠 1-16周（共 16 周）。 |
| `duplicate-course` | warning | 同一 `courseCode` 出现 ≥2 个教学班 | 《X》选了 2 个教学班，学分只会计算一次。 |
| `already-passed` | warning | 课程在成绩单中 `passed` / `in-progress` | 《X》已经修读并通过，重复修读通常不再计入学分。 |
| `credit-cap` | warning | 已选总学分 > 上限（默认 30） | 本学期计划 N 学分，超过 30 学分的学期上限。 |
| `no-meeting` | info | 教学班 `meetings.length === 0` | 《X》该教学班没有排课时间，可能是线上课程或时间待定。 |
| `out-of-term` | warning | 任一周次 > 学期 `weekCount` | 《X》有上课周次超出本学期 20 周的范围。 |
| `campus-gap` | warning | 同日相邻两节、校区不同、中间无空节 | 周三 第 4 节在仙林，第 5 节在鼓楼，两节课之间没有换校区的时间。 |
| `requirement-unmapped` | info | 课程不匹配任何培养模块 | 《X》没有匹配到培养方案中的任何模块，可能不会计入毕业学分。 |

**严重度的产品含义**：`error` 表示物理上不可能（必须处理）；`warning` 表示规则上可能有问题（值得提醒）；
`info` 表示只是信息（不打断）。界面上三者用三种颜色与三种图标区分，不合并成一个「警告数」。

### 3.2 时间冲突算法

```ts
for each pair (a, b) in selectedItems:          // 只比较已选，备选不参与
  for each meeting ma in a.section.meetings:
    for each meeting mb in b.section.meetings:
      if ma.day !== mb.day: continue
      start = max(ma.startPeriod, mb.startPeriod)
      end   = min(ma.endPeriod,   mb.endPeriod)
      if start > end: continue                  // 节次不相交
      weeks = mask(ma) & mask(mb)
      if weeks === 0: continue                  // 周次不相交（单双周走这里）
      记录 span(day, start, end, weeks)
  合并同一对课程、同一天的 span → 一条 issue（周次取并集）
```

复杂度 `O(n² · m²)`：n 为方案课程数（≤ 30），m 为每门课的排课段数（≤ 4），最坏约 1.4 万次比较，
在浏览器里 < 1ms，足以支撑每次拖拽后即时重算。

**为什么不按课程整体标红**：同一门课可能只有周一那节和别的课撞，周三那节并没有。
`WeekGrid` 依据 `issue.time` 精确标红对应格子，避免「整门课都是红的」的误导。

### 3.3 单双周的边界

```
课程 A：周一 3-4 节，1-16 周（单周）
课程 B：周一 3-4 节，1-16 周（双周）
maskA & maskB === 0  →  不冲突
```

这是本系统相对「手写课表」最直接的收益之一：人在纸上判断单双周极易出错，
而位掩码求交不会。

## 4. 培养方案核算

### 4.1 规则类型

| `rule.kind` | 含义 | 匹配条件 | 优先级 |
| --- | --- | --- | --- |
| `courseSet` | 指定课程清单 | `courseCodes.includes(course.code)` | 最高（0） |
| `tagSet` | 标签集合 | `course.tags ∩ rule.tags ≠ ∅` | 中（1） |
| `elective` | 任意选修 | 恒真 | 最低（2） |

### 4.2 分配算法

```
输入：program、transcript（passed）、planned（在修 + 方案已选）、courses（用于补标签）
输出：每个叶子节点的 earned / planned / items

1. 展平培养方案 → 叶子节点（带 rule），按「优先级 ↑，书写顺序 ↑」排序
2. 收集课程：
   - passed 记录 → source = transcript（已获）
   - in-progress 记录 + 方案 selected → source = plan（计划）
   - 成绩单缺 tags 时，用课程库补齐（教务成绩单通常没有标签）
   - 同一课程号只保留一次：passed 优先，其次计划
3. 逐门课程（已获优先 → 学分从大到小）找到第一个「匹配且未满」的节点：
   - 计入该节点；若超出要求，标记 overflow（仍计入，但界面提示溢出）
   - 找不到匹配 → 进入 unmapped（界面提示「可能不计入毕业要求」）
4. 父节点 = 子节点之和（若父节点显式给出 requiredCredits，以其为准）
5. 计算状态：met（已获 ≥ 要求） / planned（已获+计划 ≥ 要求） / short
```

### 4.3 为什么这样设计

- **可解释**：规则写死在界面上（培养方案页顶部有一行「核算口径」），用户能自己判断差异。
- **不假装知道学校规则**：真实教务可能有「就高/就低」「必修优先」等隐藏优先级，本系统不猜测，
  而是用一个公开的、确定的规则，并允许用户据实调整。
- **一门课只算一次**：避免同一门课同时满足两个模块导致「看起来毕业了」。

### 4.4 演示数据的核算例子

```
通识通修课程 45
├─ 思想政治理论 16：已获 12（4 门思政）+ 计划 3（习近平新时代…，在修）= 15 → short，还差 1
├─ 外语能力 8：已获 8 → met
├─ 体育与健康 4：已获 3 + 计划 1（体育四，在修）= 4 → planned
├─ 通识教育 12：已获 6 + 计划 2（科技与社会）= 8 → short
└─ 新生研讨与军事 5：已获 5 → met
```

`剩余 = 要求 − 已获`，`尚缺 = 要求 − 已获 − 计划`。两个数字都要展示，否则用户会误以为「在修 = 已得」。

### 4.5 真实培养方案（软件工程 2024，已验证）

教务只提供**模块级**要求（`XDYQ` 文本），没有公开的课组级要求接口，因此 v1 用四个模块：

| 模块 | 要求学分 | 匹配规则（标签） |
| --- | --- | --- |
| 通识通修课程 | 61 | `通修`、`通识` |
| 学科专业课程 | 49 | `学科专业` |
| 多元发展课程 | 34 | `多元发展` |
| 毕业论文/设计 | 6 | `毕业论文` |

课程 → 标签：

- 成绩单有 `KCXZDM_DISPLAY`（通修/通识/平台/核心/选修），直接映射；
- 课程库没有该字段，用课程号前缀推断：`000` 通修、`002/003/004/006` 通识、`2500` 学科专业、`2501` 多元发展。

该前缀规则在 55 门已修课程上 **55/55 与教务口径一致**，但仍是推断，界面需注明。

实测结果（2026-11-08）：

```
通识通修 59 + 1.3 / 61   （尚缺 0.8）
学科专业 35 + 9   / 49   （尚缺 5）
多元发展 10 + 9   / 34   （尚缺 15）
毕业论文  0 + 0   / 6    （尚缺 6）
已获 104 / 150，计划 18.3 学分，课表 0 冲突
```

### 4.6 边界情况

| 情况 | 处理 |
| --- | --- |
| 课程从未出现在课程库（只有成绩单记录） | 用成绩单的 code/credits 参与 courseSet 匹配；tagSet 无法匹配 → unmapped 并提示 |
| 同一门课重修两次 | 成绩单按课程号去重，取最高一次；`retake` 字段保留 |
| 课程学分超过模块剩余 | 全部计入，标 `overflow`；不转移到其他模块 |
| 模块 `requiredCredits = 0` | 视为无要求，不参与分配 |
| 培养方案有父节点但没有子节点 | 父节点按 `rule` 直接核算（`flattenRequirements` 保留带 rule 的叶子） |
| 计划里的课程随后被移出 | 重新计算，`planned` 归零；无需特殊处理（纯函数） |

## 5. 指标口径

所有指标都写死口径，并在界面上以 tooltip/说明呈现。**口径比数值更重要**。

| 指标 | 算法 | 口径说明 |
| --- | --- | --- |
| `totalCredits` | 已选课程学分之和（同课程号只算一次） | 不含备选 |
| `courseCount` | 已选课程号去重计数 | — |
| `activeDays` | 有排课的星期集合 | 按全学期并集，即「典型周」 |
| `earliestPeriod` / `latestPeriod` | 各天最早开始 / 最晚结束的最小/最大值 | 用于提示「晚上有课」 |
| `gapPeriods` | 每天 `(最晚−最早+1) − 实际占用节数` 之和 | 空档越多，一天越碎 |
| `weeklyPeriods` | 每周总课时 / 有课周数，保留 1 位小数 | 只在有课的周上平均 |
| `conflictCount` | `severity === 'error'` 的数量 | 与 `warningCount` 分开 |
| `loadByDay` | 每天占用的节次数 | 用于「哪一天最累」 |

### 5.1 为什么空档按并集算

学生看课表时通常忽略「第 10 周这门课就结束了」，而是看「我这学期大概什么样」。
并集口径与这种直觉一致。若按某一周计算，会出现「第 1 周没空档、第 9 周全是空档」的抖动，
反而增加认知负担。需要精确时用周次选择器（第 N 周）切换到单周视图。

## 6. 性能与数据规模

| 项目 | 量级 | 处理 |
| --- | --- | --- |
| 课程库 | 10²–10³ 门 | 一次性下发（`GET /api/catalog`），前端内存筛选 |
| 教学班 | 10³ | 同上 |
| 方案课程 | ≤ 30 | 全量分析，无增量计算 |
| 冲突检测 | ≤ 3.6 万次比较 | 每次变更即时重算，< 5ms |
| 培养方案节点 | ≤ 50 | 每次重算，< 1ms |

结论：**不需要虚拟列表，也不需要 Web Worker**。这是刻意选择——少一层异步，交互才能做到「拖进去立刻有反馈」。

## 8. 已知局限

1. **不做先修关系检查**：缺少课程大纲的稳定数据源。
2. **不处理「同一门课不同学分」**（如实验班/普通班），以课程库为准。
3. **不做跨学期路线图**：数据模型支持（`Term[]`），但 UI 只做单学期规划。
4. **学分上限是全局配置**（30），不是按专业/年级的规则。
5. **不考虑通勤时间**，只做「相邻节次换校区」的提示。
