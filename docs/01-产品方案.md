# 01 · 产品方案

> 对应选题：《学业规划与选课决策辅助系统》
> 本文回答：为谁做、解决哪个环节、做成什么样、做到什么程度算成功。

---

## 1. 问题定义

选题说明识别了四个痛点，四场景脚本又把它们各自外化成一个具体时刻。把它们对齐后，本项目的目标非常明确：

| 脚本里的时刻 | 背后的认知负担 | 现有工具为什么没解决 |
| --- | --- | --- |
| 五个页面、一张纸、全靠手抄 | 信息分散，需要人肉搬运与转录 | 教务系统按「业务」组织页面，不按「一次决策」组织信息 |
| 三张透明片叠起来一片糊 | 学分、课程、时间三个视图无法同时看见 | 课表是图片/表格，培养方案是长文档，两者不通 |
| 两列便利贴，其中一条来自三年前 | 比较时缺少来源与时效标注 | 课程详情页不标注「这条信息属于哪个学期」 |
| 三张手绘课表，纸擦出洞 | 试选成本高，不敢确定 | 正式选课不可反复试，Excel 无法校验冲突 |

一句话：**信息都在，但没有任何一个视图能让人同时看见「还剩多少学分、这些课怎么排、这个组合行不行」。**

## 2. 用户与场景

### 2.1 主用户画像

- 南京大学本科生，大二下至大四上，正在为**下一个学期**制定选课计划。
- 已经知道自己大概要修什么方向，但对「还差哪几个模块、差几分」只有模糊印象。
- 手上同时开着：培养方案 PDF、成绩单、开课列表、课表、若干课程评价帖。
- 决策时间集中在选课开放前 1–3 天，往往在晚上。

### 2.2 关键使用场景

| 场景 | 触发 | 期望结果 |
| --- | --- | --- |
| S1 盘账 | 想知道「离毕业还差什么」 | 一张按模块拆开的缺口清单，且能直接看到哪些课能补 |
| S2 试排 | 想在若干门课之间反复组合 | 拖进去就能看到冲突与学分变化，随时撤销 |
| S3 比较 | 有两三套想法，拿不定主意 | 并排对比：总学分、到校天数、冲突、覆盖度 |
| S4 定稿 | 要把结果带到正式选课页面 | 一份可打印/可导出的课程清单，含课程号与教学班 |

### 2.3 不做谁

- 不做给辅导员/教务用的管理端（不涉及他人数据）。
- 不做「抢课脚本」或自动提交（不触碰写接口）。
- 不做课程评价社区（评价数据来源不可核实，v0.1 只做占位与说明）。

## 3. 产品定位与边界

**定位**：选课前的「沙盘」。相当于把培养方案、课程库和课表叠在一张桌面上，允许用户随意挪动，且不会产生任何真实后果。

三条硬边界（写进界面文案，也写进代码）：

1. **只读**：不调用任何写接口，不产生选课结果。
2. **只本人**：只同步当前登录者自己的数据；不提供他人查询、不共享账号。
3. **不越过认证**：遇到验证码即停止，改用浏览器 Cookie 导入；不做验证码识别。

## 4. 研究问题与设计假设

**研究问题**：通过可视化约束反馈与多方案比较，能否降低制定选课计划时的信息查找成本、认知负担和判断错误？

拆成四个可检验假设，每个都对应一个具体设计：

| 编号 | 假设 | 对应设计 | 检验指标 |
| --- | --- | --- | --- |
| H1 | 把「缺口—课程—课表」放在同一屏，能减少页面切换 | 规划工作台三栏同屏；培养方案页的「可补足课程」直接可加 | 任务中页面切换次数、视线跳转次数（录屏编码） |
| H2 | 冲突解释到「哪几周、哪几节」比一个红点更有用 | 冲突条目含课程名、星期、节次、重叠周次 | 冲突判断正确率、解释后是否需要额外求助 |
| H3 | 单双周/跳周的可视化能消除「以为冲突/以为不冲突」 | 周次位掩码 + 单周切换器 + 周次文本（`1-16周（单周）`） | 单双周判断题的正确率与耗时 |
| H4 | 可撤销、可并排的多方案能降低「不敢确定」 | 方案副本、撤销栈（Ctrl+Z）、对比矩阵 | 方案创建数、反复修改次数、主观「确定感」评分 |

> 这些假设目前**没有被验证**。它们的作用是让实现有取舍依据，并直接决定 §9 的测试设计。

## 5. 信息架构

```
登录 / 数据接入
└─ 概览            盘账：进度、缺口、本周课表、我的方案、数据来源
   ├─ 培养方案      结构：模块树 → 明细（要求/已获/计划/尚缺/可补足）
   ├─ 选课规划      操作：课程池 + 周课表 + 学分账本 + 冲突清单（核心）
   ├─ 课程库        检索：筛选、状态角标、课程对比
   ├─ 方案对比      决策：指标矩阵、覆盖度、逐门课差异
   └─ 设置          信任：数据来源、作息口径、接口探针、隐私边界
```

页面职责的划分原则：**概览回答「我现在在哪」，培养方案回答「要求是什么」，规划回答「这样行不行」，对比回答「哪个更好」。**
同一个数据在不同页面有不同粒度，但**数字必须一致**（都由 `@planner/shared` 计算）。

## 6. 核心任务流

### 6.1 首次接入（目标 ≤ 90 秒）

```
登录页 → 选择「演示数据 / 统一认证 / 粘贴 Cookie」
      → 拉取培养方案、成绩、开课、课表
      → 概览页顶部显示「数据更新于 X 分钟前」与每条来源的时间
      → 若某来源失败：其余数据照常展示，失败来源标黄并给出下一步
```

关键设计：**部分失败不阻塞整体**。教务接口不稳是常态，产品必须能带着缺口工作。

### 6.2 制定一套方案（目标 ≤ 8 分钟）

```
进入规划 → 默认展示已有方案（或新建）
        → 左侧课程池默认按「可补缺口」排序
        → 把课程拖进课表（或点 +，自动选无冲突教学班）
        → 右侧学分账本实时更新：学分、门数、到校天数、周课时、空档
        → 冲突面板即时显示：「A 与 B 在周一 3-4 节冲突，重叠 1-16 周」
        → 不满意：Ctrl+Z 撤销，或把课程拖入「备选」区暂存
```

关键设计：**所有分析在本地即时完成**，网络只负责持久化；拖拽过程中不会出现「转圈等后端」。

### 6.3 比较与定稿（目标 ≤ 4 分钟）

```
复制方案 → 改几门课 → 打开方案对比（勾选 2–4 个）
        → 指标矩阵高亮更优值；覆盖度按模块并排；逐门课看谁选了谁没选
        → 选定一个方案 → 导出 Markdown / CSV / ICS
```

## 7. 功能清单与优先级

MoSCoW：M=必须（v0.1 已完成），S=应该（v0.2），C=可以（v0.3+），W=不做。

| 功能 | 优先级 | 状态 | 说明 |
| --- | --- | --- | --- |
| 培养方案进度核算 | M | ✅ | 模块树、已获/计划/尚缺、溢出提示 |
| 课程池按缺口排序 | M | ✅ | 「可补缺口」角标 + 只看缺口筛选 |
| 周课表 + 拖拽加入 | M | ✅ | 5/7 天切换、全部周/指定周、冲突条目联动 |
| 冲突检测（时间/重复/已修/学分上限/无排课/跨校区） | M | ✅ | 见 [03 算法](03-领域模型与算法.md) |
| 多方案保存、复制、撤销 | M | ✅ | 撤销栈 40 步，Ctrl+Z |
| 方案对比 | M | ✅ | 指标矩阵 + 覆盖度 + 逐门课矩阵 |
| 导出 Markdown / CSV / ICS | M | ✅ | ICS 带 RRULE，可导入日历 |
| 课程库筛选与课程对比 | S | ✅ | 最多 4 门并排 |
| 学业预警呈现 | S | ✅ | 批次状态 + 未通过课程明细 |
| CAS 登录代理 | S | ⚠️ 受滑块验证限制 | 已实现但默认不绕过；主路径为 Cookie 导入 |
| ehall 五类数据接口 | S | ✅ 已验证 | 课表/方案/成绩/开课/预警，见 [02](02-数据获取与合规.md) |
| 课组级培养要求（思政 16 等） | S | ⛔ 无公开接口 | v1 只做模块级核算 |
| 先修关系检查 | C | ⛔ | 需要课程大纲数据，暂缺 |
| 跨学期毕业路线图 | C | ⛔ | 数据模型已预留 `Term[]` |
| 浏览器扩展导入 | C | ⛔ | 选题说明中列为可选，非运行前提 |
| Agent 自然语言规划 | C | ⛔ | 规则引擎已独立，接入成本可控 |
| 课程评价 / 历史考核 | W | ⛔ | 来源不可核实，避免误导 |

## 8. 与选题说明的逐条对应

| 选题说明的要求 | 本项目的落点 |
| --- | --- |
| 选择专业与培养方案版本 | `ProgramVersion` + 设置页展示版本；当前单版本，结构支持多版本 |
| 展示各类学分要求、已完成、尚缺及可补足课程 | 培养方案页模块树 + 明细面板的「可补足课程」 |
| 课程按类别/学分/教师/时间检索 | 课程库筛选条（关键词、类别、学分、星期、缺口、无冲突） |
| 同一界面比较若干课程的关键字段 | 课程库底部对比条（最多 4 门，8 个字段） |
| 课程信息注明来源、适用学期、更新时间 | `Provenance` 字段 + 设置页来源列表 + 顶栏「数据更新于」 |
| 点击或拖动课程加入计划 | 课程卡拖拽 + `+` 按钮（自动挑无冲突教学班） |
| 考虑星期、节次、教学周、单双周 | 周次位掩码 + `WeekPattern`，冲突精确到周次 |
| 解释冲突涉及哪些课程与时段 | 冲突条目文案直接给出课程名、星期、节次、周次 |
| 保存多个备选方案并并列展示 | 方案 A/B + 对比页指标矩阵 |
| 切换、复制、替换、撤销 | 方案标签切换、复制、移除/替换、Ctrl+Z |
| 保存与导出对照清单 | Markdown / CSV / ICS 导出 |
| 课程实际时间不可拖动 | 课表位置由排课自动生成，用户只能换教学班/换课 |
| 不依赖非公开接口、不保存凭证 | CAS 只换会话；Cookie 导入为降级；探针由用户主动触发 |

## 9. 成功指标与埋点计划

### 9.1 任务级指标（可用性测试时采集）

| 指标 | 采集方式 | 基线（现有网站） | 目标 |
| --- | --- | --- | --- |
| 制定一套无冲突方案耗时 | 计时 + 录屏 | 待测（脚本中约 1h12m） | ≤ 8 分钟 |
| 页面/视图切换次数 | 录屏编码 + 前端埋点 | 待测 | 减少 50% |
| 冲突判断错误数 | 主持人观察 + 事后问卷 | 待测 | 0 |
| 求助次数 | 观察 | 待测 | ≤ 1 |
| 主观难度（1–7） | 问卷 | 待测 | ≤ 3 |
| SUS | 问卷 | 待测 | ≥ 75 |

### 9.2 产品内可采集的事件（本地、匿名、默认关闭）

```
plan.create / plan.duplicate / plan.switch
plan.item.add   { origin, courseCode, conflictBefore }
plan.item.remove
plan.undo / plan.redo
conflict.resolve  { kind, method: 'remove' | 'swap-section' | 'ignore' }
course.filter    { filters }
export.format    { format }
source.sync      { kind, result }
```

> 只记录事件类型与计数器，不记录课程名之外的个人信息；默认关闭，需在测试前明确告知并征得同意。

## 10. 非目标与伦理

- **不追求覆盖所有院系**。培养方案规则差异极大，v0.1 只保证计算机专业种子数据的正确性，其他专业需要新的 `ProgramVersion` 与映射。
- **不声称与教务口径一致**。界面上写明核算规则（「指定课程 > 标签匹配 > 任意选修」），用户可据此判断差异。
- **不制造确定感**。冲突面板只陈述事实，不替用户做决定；不出现「推荐最优方案」的自动结论。
- **不保留可识别信息**。演示数据虚构；真实数据只存本地 `apps/server/data/`，可一键删除。
